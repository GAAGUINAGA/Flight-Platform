## PUNTO 0 — paginación de las listas de v2 rota en la nube (se entrega junto con F12c-1: mismo commit de código y misma auditoría)

### Síntoma (comprobado por el humano en producción, 12-11-2026)
`GET /api/v2/vuelos/bookings?limit=5` devolvió 20 reservas; con `&cursor=<nextCursor>` devolvió la misma página con el mismo `nextCursor`.

### Causa exacta: Reservation, ni el gateway ni el ESB ni el .proto
- El .proto es correcto: `ListReservationsRequest.page = common.v1.PageRequest { cursor, limit }`. El gateway lo arma bien (`page: { limit, cursor }`, `v2/booking.controller.ts:35` y `booking.controller.ts:13` de v1). El ESB reenvía el `input` intacto (`ExecuteOperation.rpc`: `invoker.invoke(service, method, request.input, …)`; solo las operaciones compuestas filtran campos con `pick`, y `reservas.listar` no es compuesta).
- En Reservation el controlador gRPC valida con Zod (`page: { cursor, limit }`, correcto) y entrega el objeto TAL CUAL a `composeReservation`, que hace `listReservations: (value) => queries.list(value)`. Pero `ReservationQueries.list` lee `limit` y `cursor` **planos** (`input.limit ?? 20`, `input.cursor`). `page` era un campo anidado que el caso de uso nunca miraba: `limit` valía siempre 20 (los «20 reservas» de producción) y el cursor no llegaba al almacén, así que cada llamada devolvía la primera página y el mismo `nextCursor` (id de la reserva 20ª). Ningún error: los tipos pasaban por `queries.list(value as never)`.
- El almacén (Prisma e InMemory) paginaba bien (`take: limit + 1`, `cursor: { id }, skip: 1`).

### Corrección
`microservices/reservation-service/src/infrastructure/grpc/reservation.controller.ts`: nuevo `flattenPage` en el adaptador gRPC (la capa que habla el idioma del .proto) que convierte `page { cursor, limit }` en `limit` y `cursor` para el caso de uso. No se cambió ningún contrato (ni el OpenAPI v2 ni el .proto: no se quitó ni se agregó nada) ni `domain/` ni `application/`.
