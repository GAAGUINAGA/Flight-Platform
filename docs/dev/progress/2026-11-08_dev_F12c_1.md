# Bitácora — F12c-1: verificación de pagos de Booking en la nube (corrección corta)

Rol: Developer. Rama `fix/pago-cubre-tarifa`, desde `main` (e5536aa). F12b-2 queda pausada en `feat/F12b2-bus-eventos` (067b3d1, sin cambios pendientes; no se tocó).

## Notas de la entrega (resumen)
Booking opera contra nuestra nube. API de pagos: `GET https://booking-core-api.azurewebsites.net/api/v2/pagos/{paymentReference}`, cabecera `X-Api-Key`. En compras reales Booking cobra 693 = nuestra tarifa 630 + su servicio 63; el monto del pago es el total cobrado. Un pago exitoso llega con `status: CAPTURED`. Configuración ya aplicada a mano en Cloud Run (reservation-service): `BOOKING_PAYMENTS_BASE_URL`, `BOOKING_PAYMENTS_AUTH_HEADER=x-api-key`, secreto `BOOKING_PAYMENTS_AUTH_VALUE=booking-payments-auth:latest`; sin `BOOKING_PAYMENTS_STATUS_MAP`.

Evidencia de producción (08-11-2026, 23:03 y 23:04 UTC, compras reales de Booking del FP103): Reservation consultó la API de pagos de Booking y rechazó con 422 PAYMENT_NOT_AUTHORIZED; log: [BookingPayments] payments api returned an unmapped status value="CAPTURED". Los pagos eran de 693 (630 de nuestra tarifa + 63 del servicio de Booking). Con CAPTURED reconocido, la regla actual de monto igual también los habría rechazado: por eso van juntos los cambios 1 y 2.

6. Declara también en deploy-reservation.yml el resto de la configuración de pagos que hoy está a mano en Cloud Run (punto 6 ajustado). En las notas originales el punto 6 decía que no hacía falta `BOOKING_PAYMENTS_STATUS_MAP` en el workflow y que se documentara cómo pasar un JSON con comas; ambas cosas quedan en el ADR (sin mapa propio; documentado el separador `^@^`).
