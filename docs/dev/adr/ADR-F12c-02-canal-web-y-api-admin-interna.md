# ADR-F12c-02 — Canal de pago WEB (B-1) y API interna de administración (B-2)
- Estado: Aceptado (decisiones Q11, Q12 y Q13 del humano, 2026-11-11) · Fecha: 2026-11-11 · Fase/Tarea: F12c backend previo
- Diseño de origen: `docs/dev/f12c0-diseno-front.md` §5, §12, §14 · ADR: `ADR-F12c-01-front-graphql-react.md`
## Contexto
El front usa solo v2. Un usuario de Supabase (cliente o admin) no pasaba por la verificación de Booking: caía en el verificador simulado por omisión de Reservation (sin canal), sin `deferIssuanceFailure` y sin forma de apagarlo. Además, el panel necesitaba la lista de vuelos con `flightInstanceId` y las tarifas, que solo existían en `/flights/v1/admin` (contrato v1 deprecado).
## Decisión B-1: canal `WEB` (pago simulado de prueba)
1. **El canal lo asigna el Gateway solo por el rol del token** (`channelFor`): un token de socio (`clientId`) usa `BOOKING`, con su verificación y su marca de venta sin cambios; cualquier otro usuario autenticado (cliente o admin de Supabase) usa `WEB`. Ni el cuerpo (`salesChannel`, `payment.provider`) ni cabeceras lo deciden. Aplica a crear reserva, equipaje y cambio de fecha con pago. `deferIssuanceFailure` se envía siempre (también a clientes).
2. **Interruptor `WEB_PAYMENT_MODE`, sin valor por omisión que venda.** Solo el valor exacto `simulated` habilita el canal; ausente o desconocido = deshabilitado. El Gateway rechaza antes de tocar el hold (422 `PAYMENT_NOT_AUTHORIZED`, `type` `web-payments-disabled`) y avisa al arrancar (`warnWebSales`). Reservation vuelve a exigirlo: su verificador `WEB` (`WebPaymentVerifier`) rechaza con `PAYMENT_NOT_AUTHORIZED` si no está en `simulated` (defensa en profundidad) y también avisa al arrancar. Con `simulated` aplica las reglas del verificador simulado (`pay_ok_*`, `pay_pending_*`, …).
3. **Topes por usuario** (`WEB_MAX_ACTIVE_BOOKINGS`=5 reservas activas —no canceladas ni fallidas, contadas en Reservation— y `WEB_MAX_PASSENGERS_PER_DAY`=10 pasajeros en 24 h, contados en el estado v2 del Gateway). Superarlos → 429 `RATE_LIMIT_EXCEEDED` con `type` `web-active-bookings-limit` / `web-passengers-per-day-limit`. Un reintento con la misma `Idempotency-Key` no los recuenta. Valores no enteros positivos impiden arrancar.
4. **Correo confirmado.** Se exige el claim `email_verified: true` de **nivel superior** del JWT (no `user_metadata`, que el usuario puede editar). Sin él → 403 `FORBIDDEN`, `type` `email-not-verified`. El claim lo debe agregar el hook de Supabase desde `auth.users.email_confirmed_at` (`docs/dev/f11a-supabase-auth-hook.sql` actualizado; lo aplica el humano): **hasta que se aplique, la web no puede reservar** (falla cerrado). `WEB_REQUIRE_VERIFIED_EMAIL=false` solo se admite fuera de producción.
5. **Reservas de prueba identificadas.** Reservation guarda `payment_channel = WEB` (columna existente `VarChar(16)`); el estado v2 guarda `salesChannel = { partnerId: 'WEB_TEST', passengers: n }`, que además viaja en el `BookingDetail` (propiedades adicionales permitidas por el esquema). Para el administrador: `GET /api/admin/v1/web-bookings` (solo lectura; `owner` es un hash opaco, sin sub, referencia de pago ni datos personales).
6. **Errores del catálogo sin tocar el contrato v2:** los rechazos usan `code` del enum de `ProblemDetails` v2 y un `type` propio (`https://flight-platform.dev/problems/<tipo>`), que el front usa para distinguir el caso. Solo los ve un usuario del canal WEB; un socio nunca los recibe.
7. **Sin `.proto` ni migración.** Solo se amplía el enum de validación Zod de `paymentChannel` de Reservation (`BOOKING` | `WEB`). El contrato v2 con Booking no cambia.
8. **Despliegue.** Reservation (Cloud Run): `WEB_PAYMENT_MODE=simulated` declarado en `extra_env_vars` de `deploy-reservation.yml` (la capacidad). El Gateway se despliega en Render sin workflow de despliegue (solo `gateway-ci.yml`): sus variables (`WEB_PAYMENT_MODE`, `WEB_MAX_ACTIVE_BOOKINGS`, `WEB_MAX_PASSENGERS_PER_DAY`) se declaran en `platform/api-gateway/.env.example` y en la guía `docs/dev/f12c-backend-previo-despliegue.md`, y `scripts/ci/check-deploy-env.cjs` verifica ambas cosas. **Quien decide vender es el Gateway**: sin `WEB_PAYMENT_MODE=simulated` en Render no se vende aunque Reservation lo permita.
## Decisión B-2: API interna de administración, versión 1 (`/api/admin/v1`)
1. Prefijo propio con su **OpenAPI interno** `contracts/openapi/interno/admin-v1.yaml`, separado de `vuelos-openapi.yaml` y `vuelos-openapi-v2.yaml` (que no cambian). **«v1» es la primera versión de esta API interna y no tiene relación con el contrato v1 deprecado**; así consta en el OpenAPI.
2. Solo rol `admin` con `flights:admin`; un `customer`, un `partner` (aunque lleve el scope) o un admin sin el scope reciben 403; sin token o inválido, 401. La autorización ocurre **antes** de validar el cuerpo. Errores en el formato `ProblemDetails` de v2 (`isV2Path` incluye este prefijo para autenticación y errores).
3. Reutiliza los manejadores de `AdminController` (mismos esquemas Zod, mismas llamadas a Inventory y Pricing). Operaciones: `GET /flights` (con `flightInstanceId`), `GET /fares`, `PUT /fares`, y `GET /web-bookings` (B-1.5). Crear y cerrar vuelo, y las actualizaciones operacionales (se usa el `PATCH` de v2) quedan fuera (decisión Q3).
4. Se valida con `express-openapi-validator` sobre el OpenAPI interno (y respuestas en desarrollo y pruebas). Las rutas `/flights/v1/admin/*` **no se tocan** en esta entrega (retirarlas junto con v1 es una decisión posterior; hoy el panel ya no debe usarlas).
## Consecuencias
- Pruebas: `platform/api-gateway/src/v2/web-sales.spec.ts`, `src/admin-api.spec.ts` (incluye aislamiento cliente/cliente/socio) y `microservices/reservation-service/test/f12c-web-payments.spec.ts`.
- Requiere para vender: `WEB_PAYMENT_MODE=simulated` en el Gateway (Render) y el hook de Supabase con el claim `email_verified` (humano).
- El canal WEB entrega boletos de prueba sin cobro por diseño; los topes y el interruptor limitan el abuso del inventario y del stock que se sincroniza con Booking.
- Pendiente fuera de esta entrega: puerta de embarque y salud del bus (BACKLOG), precalentamiento del servicio GraphQL.
