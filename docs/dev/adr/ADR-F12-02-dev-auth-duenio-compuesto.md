# ADR-F12-02 — dev-auth `client_credentials` y dueño compuesto `<clientId>~<X-User-Id>`
- Estado: Aceptado · Fecha: 2026-10-26 · Fase/Tarea: F12a P1 (decisión D1 del humano)
## Contexto
El contrato v2 declara `PartnerOAuth2` (`client_credentials`, `tokenUrl: /oauth2/token`) emitido por el `dev-auth` de la aerolínea y que Booking reenvía el usuario final en `X-User-Id`. Si el dueño de un recurso fuera `X-User-Id` a secas, Booking podría fabricar el `sub` de un usuario de Supabase y leer sus reservas; además Webhooks entrega por dueño exacto (ADR-F11-18), así que la suscripción de Booking no recibiría eventos de los usuarios que reenvía.
## Decisión
- `POST /api/v2/oauth2/token` (RFC 6749 §4.4): `client_id`/`client_secret` por form, JSON o HTTP Basic; scopes pedidos ⊆ scopes del cliente (`invalid_scope`); `invalid_client` idéntico para cliente inexistente y secreto erróneo (hash señuelo para igualar el tiempo); tras N fallos por minuto del mismo cliente, 429 `temporarily_unavailable`. Ruta fuera del contrato (solo declara `tokenUrl`), documentada en la guía para Booking.
- `GET /api/v2/.well-known/jwks.json`: solo la llave pública (`kid` = huella JWK, RS256). La privada llega por `DEV_AUTH_PRIVATE_KEY` o `DEV_AUTH_PRIVATE_KEY_FILE`; sin ella (solo fuera de producción) se genera una efímera al arrancar. En producción el dev-auth queda apagado si faltan llave y `PUBLIC_BASE_URL` https. Nunca se versiona ni se registra.
- Clientes en `gateway.dev_auth_client` (`client_id`, `secret_hash`, `scopes[]`, `active`). Secreto de 256 bits, guardado con scrypt (sal por cliente, parámetros dentro del hash); se entrega una sola vez por `npm run dev-auth:client` (archivo 0600 fuera de git, o `--print` explícito). `client_id` cumple `^[a-z0-9][a-z0-9-]{2,39}$`: **nunca contiene `~`**.
- Verificación en proceso (sin autollamada HTTP), con emisor `${PUBLIC_BASE_URL}/api/v2` y audiencia `flight-platform`. Un cliente desactivado pierde acceso aunque su token no haya vencido (caché de cliente de 5 s).
- Dueño (D1): con token de partner, `ownerId = "<clientId>~<X-User-Id>"`; sin `X-User-Id`, `clientId`. `X-User-Id` debe cumplir `^[A-Za-z0-9._:@+-]{1,64}$` (sin `~`; el compuesto cabe en los 128 caracteres de los servicios). Con tokens que no son de partner `X-User-Id` se ignora y el dueño es el `sub`.
- Webhooks (se implementa en P3): las suscripciones son del cliente (`<clientId>`) y reciben los eventos de todos los recursos `<clientId>~*`. Como el `clientId` no contiene `~`, un cliente no puede construir un dueño de otro cliente ni el `sub` de un usuario de Supabase.
- `flights:ops` se suma a los scopes; las operaciones de panel aceptan `flights:ops` **o** `flights:admin` (`AnyScope`).
## Consecuencias
Los tokens de v1 y el emisor de desarrollo siguen igual. La migración `20261026000000_gateway_dev_auth` crea una tabla en el esquema `gateway`; la aplica el humano.
